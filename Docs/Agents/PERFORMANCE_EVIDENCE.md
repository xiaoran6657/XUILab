# 性能实验与证据规范

本规范落实[路线图第 8 节](../MVP/ROADMAP.md)；它不声明当前已有 Runner、测试或性能结果。正式实验参数在 M0 校准后落盘并版本化，不能在看到结果后更换判定规则。

## 1. Agent 与 Runner 的边界

Agent 负责提出问题、设置 Case、构建、启动、等待、收集、检查有效性、分析与出图。Unity C# Runner 负责确定性动作、预热、采样、功能断言、超时和结束后导出。采样准确性不能依赖模型响应时间、鼠标动作或每帧 MCP 调用。

M0 先打通“一个基础 Case → Windows Player → 原始样本 → 有效性判定 → 报告”，并以故意失败、超时／缺失指标等反例证明不会假通过。Agent 自动化展示要包含至少一个失败被正确识别的案例。

## 2. 证据分层

| 层次 | 能证明 | 不能替代 |
| --- | --- | --- |
| 源码／合同审查 | 算法、所有权、依赖与潜在缺陷 | 实际运行正确性 |
| EditMode | 纯逻辑、索引、池不变量、采样／统计逻辑 | 生命周期、渲染效果 |
| PlayMode | Bind／Unbind、滚动、销毁／禁用、Mesh 和组件集成 | 目标 Player 的正式性能 |
| Windows Player | 对应构建、设备和配置下的行为与帧时 | 其他平台或另一种构建配置 |
| 截图／视频／重型 Profiler 捕获 | 视觉效果、流程和瓶颈诊断 | 独立正式采样数据 |

Editor 与 Player 共享资源的方式不同，Editor 数据适合快速定位，正式展示数字应来自目标 Player。Deep Profiling 会增加开销，诊断采集应与性能基准分开。[Unity 2022.3 官方说明](https://docs.unity3d.com/2022.3/Documentation/Manual/profiler-profiling-applications.html)

Development Player 可用于诊断和具备必要指标的受控比较；Release 展示包另做运行与视觉验收。不要把 Development 的计数器和 Release 的帧时拼成同一条结果；指标在当前构建不可用时缩小结论范围。

## 3. 先写实验合同

每个实验至少明确：

1. **问题与假设**：例如“总数据量增加时，活跃 Cell 是否受可视范围约束”；不预设一定快多少。
2. **A/B 和不变量**：同一数据、随机种子、视觉内容、字体、模板、可见数、动作、Canvas 配置；一次主要改变一个因素。普通列表基线应是合理实现，不故意每帧 Instantiate。
3. **动作与采样口径**：按帧还是时间驱动、开始／结束点、冷开与稳态、刷新频率；A/B 必须相同，速度改变不能偷偷改变工作量。
4. **环境**：代码／构建身份、包锁、OS、CPU、GPU、驱动、图形 API、分辨率、颜色空间、质量、VSync／限帧、后端、Editor／Player、Development／Release。
5. **指标**：名称、单位、数据源、采样时点、required／optional、不可用处理。总帧时不能命名为主线程 CPU 耗时；GPU 不可用不能用 CPU 替代。
6. **有效性与比较方法**：预热、窗口、重复次数、运行顺序、失焦／暂停／超时规则、统计方法及差异阈值来源。

起始稳态协议为预热 300 帧、采样至少 1800 帧且覆盖完整动作、独立运行 5 次；M0 根据稳定性修订后锁定。独立运行应重新建立规定的初始状态，不能把一条连续序列切五段当作五次独立运行。冷开单独定义，不把预热后的数据称作冷开。

## 4. 三类案例的重点

| 案例 | 正确性先决条件 | 性能与学习问题 |
| --- | --- | --- |
| ListLab | 池不会重复归还／同时借出同一实例；复用状态被清理；多模板、边界滚动、Wrapper 与位置恢复正确 | N 增加时活跃／空闲／总实例分别如何变化；冷开、稳态、GC；单项刷新相对全量刷新的收益和失效成本 |
| GradientLab | 渐变方向、曲线语义、颜色／Alpha、UV／顶点属性、降级边界符合合同 | 固定细分与自适应细分的段数—误差—重建成本；静态和动态过渡分别测量 |
| 自动性能测试 | 不漏掉失败／无效运行；配置和产物完整关联；统计逻辑可核对 | 同协议复跑是否稳定；自动化省去哪些重复步骤；哪些观察仍需要人工视觉判断 |

历史材料中的 FPS、实例数和优化百分比是背景，不是本项目基线。特别区分“活跃 8 个”和“池内总共 8 个”；静态代码风险不直接等于旧完整项目已发生故障。

## 5. 采集与统计

- A/B 交错运行，固定或预设顺序；保留每轮结果与轮间波动，不挑最好一轮。
- 保存原始逐帧序列，报告 p50／p95／p99、最大值、超预算帧比例。固定分位数算法；同时展示每轮统计，不靠合并所有帧掩盖运行间差异。
- 60 FPS 体验模式和不限帧吞吐模式分别报告；单个 FPS 数字不能解释瓶颈。
- 区分分配量、GC 次数、存活对象和资源内存。没有 GC 回收不代表零分配；重复压力后内存增长要结合对象／资源归属诊断。
- 采样缓冲预分配；窗口内不截图、录屏、逐帧日志或写文件，窗口结束后导出。采集开销先通过空 Case 或对照验证。
- 无效运行也归档。按预设规则标 invalid，不临时删除大帧；采样开始前失败就不生成虚假的 samples。

比较结果分别填写 correctness、measurement validity 和 performance comparison。若正确性失败，不发布性能改善结论；required 指标缺失或身份不匹配，测量无效；噪声大于效果时可以 inconclusive。功能正确但性能负收益仍是有效学习结果，应解释原因及保留／回退决定。

## 6. 产物与关联

建议每次运行使用 `Artifacts/<run-id>/`，最少保存：

```text
config.json          # Case、动作、采样协议及版本
environment.json     # 设备、构建配置、实际指标能力
identity.json        # candidate-id、commit/dirty、build-id、输入与文件哈希
samples.csv          # 实际进入采样后产生的原始序列
summary.json         # 分层状态、统计、缺失值及原因
report.md            # 可阅读结果与限制
events.log           # 阶段、失焦、异常、失败；不要求逐帧打印
```

文件名是后续 Runner 的目标合同，不代表当前已有实现。失败发生在环境探测前时如实保存可得字段并标 unknown。报告链接到真实存在的产物；原始数据、配置和构建身份应可相互校验。哈希证明关联与完整性，本身不证明测量方法正确。

无提交或工作树修改中的运行标为探索性；即使有哈希，也不能冒充正式冻结证据。M4 正式基准使用干净、可复建的版本，记录代码提交、依赖锁、构建／配置／原始数据哈希。若需改变归档方式，先更新明确的证据合同。

M4 每个主题整理封面、说明图、短视频、技术说明和数据索引。媒体录制另跑，画面实时数字仅用于解释，正式数字引用独立 run-id；加速、剪辑和跨运行拼接明确标注。个人复现、后续改进、第三方来源和历史工作贡献分别说明。

## 7. 学习闭环

每项深入实验输出一段可复述的解释：观察 → 假设 → 改动 → 同条件复测 → 原因／替代解释 → 适用边界 → 下一步。保留未奏效的方案和证据，不只保留胜利曲线。

技术验收与用户学习复盘分别记录。用户尚未安排复盘不阻塞常规实现与取证；最终索引要能看到两项核心实验是否已经完成解释复盘。
