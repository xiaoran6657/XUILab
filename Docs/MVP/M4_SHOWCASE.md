# M4：证据冻结与展示交付

规划状态：待开始。实际状态由 `Docs/PM/` 维护。

前置：[M1](M1_LIST_LAB.md)、[M2](M2_GRADIENT_LAB.md)和 [M3](M3_OPTIMIZATION.md)完成，测量协议已经锁定。

完成后：形成无需先搭建个人主页即可保存和评审的 MVP 资料包。

## 1. 主题与目标

把已验证实现、性能实验和学习过程冻结为可重建、可解释、可公开审查的 Windows MVP。M4 不再为了美化数字改变被测实现；发现问题时回到相应任务修复并使受影响证据失效。

## 2. 阶段成果

- 干净、可重建的最终源码候选、依赖锁、实验协议和证据索引。
- Windows x64 Release 展示构建，以及与 Development 测量构建分开的身份和验证。
- List Lab、Gradient Lab、Agent 自动测试三组封面、说明图和短视频。
- 三份作品案例说明、自动化复跑 playbook、来源／许可说明和 MVP 验收记录。
- 能由图表追溯到 run-id、原始数据、统计方法、构建与硬件的资料结构。

## 4. M4-01：冻结最终候选

冻结前确认：

- 所有 required 正确性、Review 和 Verification 对应同一最终候选。
- `ProjectVersion.txt`、manifest／lock、相关 ProjectSettings、Assets／`.meta`、Runner、配置和数据生成脚本在清单中。
- 工作树干净，提交可从新检出重建；依赖中的可移动引用已记录实际解析身份。
- 代表实验使用锁定协议重新构建、重新运行，不沿用受影响的旧二进制或旧数据。
- 原始数据 hash、build-id、run-id、环境和图表输入可互相校验。
- 第三方源码、字体、图片、图标和参考实现具有清楚来源与许可。

最终代表矩阵不必复跑所有探索组合，但至少覆盖公开文案中的每条结论、两项深入实验和一个失败／invalid 自动化案例。未选组合保留为探索结果，不能在文案中写成全面结论。

## 5. M4-02：Release 展示构建

生成独立 Windows x64 Release 目录，固定产品名、分辨率／窗口模式、场景列表、颜色空间、图形 API、质量和输入说明。构建包包含展示需要的诊断切换，不包含开发密钥、参考源码、个人路径或原始公司素材。

Release 验证至少覆盖：冷启动、三个主题入口、A/B 切换、核心参数、首尾滚动、位置恢复、渐变过渡、窗口缩放／目标分辨率、重复退出／启动和无未解释异常。Release 体验数字不与 Development Profiler 计数器拼成同一运行。

记录压缩前后目录、可执行文件和关键 data 的哈希、构建日志、目标提交与运行说明。若展示包无法从冻结提交复建，M4-02 不通过。

## 6. M4-03：图表与媒体

### 每个主题的最低素材

| 主题 | 图片 | 视频 | 必须讲清的内容 |
| --- | --- | --- | --- |
| List Lab | 1 张封面、2–4 张说明图 | 30–60 秒 A/B | N 与实例规模／冷开、池契约、Wrapper、局部更新结果 |
| Gradient Lab | 1 张封面、2–4 张说明图 | 30–60 秒渐变与网格 | 曲线语义、fallback、segment—误差—成本、自适应结论 |
| Agent 自动测试 | 1 张封面、2–4 张流程／结果图 | 运行与失败识别短视频 | 配置驱动、状态机、validity、失败不会假通过、复跑方法 |

图表由脚本从固定 summary／samples 生成，保存脚本版本、输入 run-id、单位和统计说明。轴不得截断或混用不同协议而不标注；压力档失败在图中用状态表达，不能删除。

媒体在独立运行录制。画面可展示诊断叠层，但正式数字引用冻结 run-id；加速、暂停、跨运行拼接和后期标注必须说明。截图保留原始图、裁剪版和用途索引。

视觉方向保持中性、清晰，先服务技术解释：统一 16:9／作品页所需版式、颜色、字号和安全边距。是否为个人主页重新设计不阻塞 M4。

## 7. M4-04：案例结构

每份案例说明使用同一骨架：

1. **背景与约束**：实习中遇到的类别问题，以及原始证据缺口。
2. **我的工作边界**：第三方基础、个人复现和后续改进分别是什么。
3. **技术问题**：可复现现象、正确性风险和性能假设。
4. **设计与实现**：关键合同、备选方案和为何选择当前方案。
5. **验证方法**：场景、A/B、公平条件、正确性和 validity。
6. **结果**：图表、效果量、轮间波动、失败／负结果和限制。
7. **学习与适用边界**：能推广的原则、不能推广的结论和下一步。
8. **复跑与证据**：构建、run-id、原始数据和脚本索引。

Agent 自动测试案例强调可重复性和错误识别，不以 Agent 数量、工具调用次数或无人值守时长作为核心成果。

## 8. 公开与隐私检查

- 不直接公开公司私有代码、内部路径、账号、服务配置、未脱敏日志或来源不明素材。
- 历史简历和任务描述只引用可公开的个人贡献；无法确认的数字标为历史记录且不用于新结论。
- 第三方许可证和修改说明随源码／案例保留；无法再分发的资产替换为自制或许可明确版本。
- 硬件和环境信息满足复现实验所需，但删除用户名、机器 ID 和无关目录。
- 发布到个人主页、公开仓库或视频平台是独立操作，需要对应用户授权；M4 本地资料包不自动发布。

## 9. MVP 最终验收

- 固定 Unity 版本、依赖和最终提交可重建，Windows Release 包在目标环境运行。
- List／Gradient required 回归和两项优化决策通过，未验证项明确。
- 每条公开性能结论可定位到有效 run、原始数据、统计、构建和环境。
- Runner 能展示正常、fail、invalid，错误状态没有被报告为 success。
- 三个主题的图片、视频、说明和数据索引齐备，链接及哈希有效。
- 来源、许可、个人贡献和结果边界完成审查。
- 用户完成两项核心实验的解释复盘；技术完成与复盘状态分别记录。

验收记录列出所有 required 项及证据，不用“整体看起来完成”替代逐项判断。发现冻结后源码变化时生成新 candidate，受影响构建、验证和媒体重新关联。
