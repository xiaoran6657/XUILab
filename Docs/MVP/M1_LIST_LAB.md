# M1：List Lab 正确性与基准

规划状态：待开始。实际状态由 `Docs/PM/` 维护。

前置：[M0](M0_FOUNDATION.md)出口通过，Runner 和测量协议 v1 可复用。

后继：列表集成场景解锁 M2 对应检查；有效基线解锁 M3-L1／L2。

## 1. 主题与目标

重建 LUI 风格列表的核心契约，以中性排行榜展示数据规模增长时 UI 实例如何保持有界、复用时内容和状态如何保持正确。首先修复复制材料中“实例归属映射依赖池幂等，但复制池只有 Stack”的契约缺口，再讨论性能。

虚拟化基础能力与个人改造分别说明。M1 不复刻完整 LUI 库，不把原公司代码直接复制进 Runtime，也不把历史 `cellMax=8`、p95 或 FPS 当作当前验收值。

## 2. 阶段成果

- 锁定版本与许可的滚动后端或独立实现边界，以及第三方变更记录。
- 可公平切换的普通 ScrollRect 基线和虚拟列表。
- 明确的池所有权、Bind／Unbind、模板路由、销毁和恢复位置合同。
- EditMode／PlayMode 正确性回归、Windows Player A/B 原始数据和分析。
- 列表诊断面板、说明图和 30–60 秒演示草稿。
- 对虚拟化成本、剩余 O(N) 工作和生命周期错误的学习复盘。

## 4. M1-01：冻结列表合同

若使用 LoopScrollRect，上游仓库、commit、MIT 许可、导入文件和本项目修改必须记录；安装包源码或 GitHub 默认分支不能代替锁定 commit。原实习项目补丁未随材料提供，不声称复刻其精确版本。

Task Brief 在实现前决定：

- 数据源如何提供 count、stable item id、template key、尺寸和绑定数据。
- Cell 的 Create／Rent／Bind／Unbind／Return／Destroy 顺序，哪些状态由 Binder 重置。
- 池按 template key 路由，如何维护 `leased instance IDs` 和唯一 cached 实例；重复 Return 的行为及诊断。
- 被销毁／失效对象如何从租赁和缓存移除；清空、禁用、销毁时谁拥有清理责任。
- 固定行高、视口、预取、缓存上限、模板集合及布局后端。
- 位置身份是 top index + offset、normalized position 或业务 item id；恢复时如何处理数据变化和越界。
- `active`、`leased`、`cached`、`created`、`destroyed`、`unowned` 和 unique total 的口径。

最低不变量：同一 Unity 实例不能同时租给两个可见项；重复归还不能把同一引用压入池两次；Bind 与 Unbind 可审计；实例归属和诊断计数按身份去重。

## 5. M1-02：实现与公平基线

普通列表使用标准 ScrollRect、RectMask2D 和合理布局，在一次数据装载时创建 N 个 item；滚动时不故意 Instantiate／Destroy。虚拟列表使用同一 item prefab、字体、图标、Binder 和布局语义，只为可见窗口及预取范围保留实例。

首期固定行高和单模板，减少尺寸与模板分布干扰。双模板用于路由正确性，不混入主性能结论。虚拟列表仍保留“刷新可见窗口”的基线行为，供 M3 的真正单项更新对照。

池实现应有明确的 active lease 集合与 cache 容器。Return 先验证归属和租赁状态，再重置并进入缓存；未知、重复或已销毁实例产生可测试的拒绝／诊断，不继续缓存。Get 清理失效引用，并在无可用缓存时创建新实例。开发诊断不应在正式采样每帧分配字符串。

## 6. M1-03：展示与生命周期

- **位置恢复**：覆盖同数据重建、数据缩短、目标 item 移除、首尾、offset 精度和惯性复位。
- **动画 Wrapper**：LayoutGroup 控制外层 Cell，动画控制内层 Wrapper；复用前恢复 scale、alpha、position 和进行中的过渡。
- **双模板**：至少两种可辨识模板，验证 template key 改变和跨窗口往返不会错池。
- **边缘渐隐**：作为显示附加效果，不改变主列表实例和滚动动作；开启／关闭分别验证材质、裁剪和输入。
- **诊断层**：显示 N、visible、leased、cached、unique created、Bind count 和当前 Case；测量模式可隐藏且不污染采样。

异步头像竞态进入扩展队列。M1 可以预留取消／版本 token 接口，但不为此引入网络或完整资源系统。

## 7. A/B 实验合同

| 维度 | MVP 配置 |
| --- | --- |
| 数据量 | 100、1000 为共同主矩阵；流程稳定后 10000 压力档；300 为历史规模参考 |
| 模板 | 主矩阵单模板；双模板为正确性 Case |
| 动作 | 冷开、预热静置、固定轨迹连续滚动、首尾跳转、位置恢复、清空重填、重复开关 |
| 环境 | 相同 Player、分辨率、Canvas、字体、素材、行高、视口、裁剪、VSync／限帧和动作时间线 |
| 功能计数 | create／destroy、Bind／Unbind、active／leased／cached、unique total、位置误差 |
| 性能指标 | 帧间隔、CPU／UI marker、GC、首次可交互、布局／网格重建；支持时记录 batches／vertices |

10000 压力档若合理普通列表超出时间或资源预算，保存失败阶段和共同规模数据，不降低内容复杂度或无限重试。冷开与预热复用分开；首次遇到新模板和窗口扩容不称作稳态零创建。

## 8. 正确性与验证矩阵

| Case | 必须成立 | 主要证据 |
| --- | --- | --- |
| 重复归还 | 同一实例不会被连续租给两个项，计数不重复 | EditMode 池不变量、诊断事件 |
| 销毁／脏引用 | 失效对象不会再次 Rent，清理后归属收敛 | EditMode + PlayMode 生命周期 |
| 滚动首尾 | item、index、template 和可视位置正确 | 动作日志、状态断言、截图 |
| 清空／重填 | Bind／Unbind 配对，无旧内容或旧动画回写 | 事件序列、视觉证据 |
| 禁用／重开 | 缓存策略符合合同，unique total 不随轮次无界增长 | 多轮曲线、对象身份 |
| 位置恢复 | index／item id 与 offset 在预定容差内 | 数值断言和截图 |
| 双模板 | 归还原池、重新租出模板匹配 | pool key／instance 日志 |
| 稳态滚动 | 固定窗口充分预热后不持续创建销毁 | Player 原始计数与帧序列 |

布局／网格重建不能仅从 Bind 次数推断；使用实际 marker 或显式诊断解释两者关系。内存曲线需结合唯一实例和资源所有权，不能单独证明没有泄漏。

## 9. 出口门槛

- 所有池与复用 required Case 通过；重复归还缺口有可复现测试和修复证据。
- 普通／虚拟列表在共同规模下使用相同输入和动作，并产出有效 Windows Player A/B。
- 虚拟实例数量对 N 保持有界，实际预算由视口、预取和模板合同解释，不写死为 8。
- 冷开、滚动、恢复、清空和重开的功能与性能结论可追溯到 run-id。
- 第一组说明图和短视频草稿存在；其中实时叠层不被当作正式数据。

学习检查：解释虚拟化减少了哪些 GameObject／布局／渲染准备成本、哪些数据或索引工作仍为 O(N)，并能说明一次布局与动画冲突、一次池归还错误的根因和保护机制。

## 10. 风险与停止条件

- 上游版本或许可无法确定：可实现独立最小后端，但必须改变来源表述；不能声称是精确 LoopScrollRect 复现。
- 普通基线无法承担高 N：保留共同规模和压力失败，不削弱其正确实现。
- marker 在 Player 不可用：功能计数仍继续，指标按协议降级或判 invalid；不能用 Editor 值替代。
- 多模板或渐隐引入干扰：从主单模板性能矩阵拆出，不阻塞核心虚拟化结论。
