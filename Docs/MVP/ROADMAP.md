# XUILab 项目路线图

更新日期：2026-09-05  
依据：[已认可的项目分析报告](../PROJECT_ANALYSIS.md)  
当前状态：路线图已编制，M0–M4 均未开始；本文件不代表工程、测试或性能结果已完成。

## 1. 项目目标与固定决策

XUILab 是一个 **Unity UGUI 性能实验与技术案例展示项目**。围绕虚拟化列表、程序化渐变和 Agent 自动化性能测试，形成“问题复现 → 正确性验证 → 性能定位 → 改进对照 → 展示资料”的完整过程，同时提高开发者本人解释和解决性能问题的能力。

### 1.1 已确定的技术基线

| 项目 | 决策 |
|---|---|
| Unity Editor | **2022.3.45f1c1**，MVP 全程固定 |
| 渲染与 UI | 与该 Editor 匹配的 URP、UGUI、TMP；具体包版本在 M0 验证并锁定 |
| 第一目标平台 | Windows x64 Player |
| 实验工具 | Unity Profiler、ProfilerRecorder、适配版本的 Test Framework / Performance Testing；按需使用 UI Profiler、Frame Debugger、Memory Profiler |
| Agent 操作 | 工程文件与构建脚本负责可重复执行，Unity MCP 负责编辑器操作和诊断；连接能力在 M0 实测 |
| 工程数量 | 一个 Unity 工程，组件、展示模式和测量模式共用实现 |
| 展示载体 | 中性排行榜和渐变实验面板；使用模拟数据、自制或许可明确的素材 |

本轮版本决策覆盖分析报告中的候选版本建议。MVP 不安排 Unity 6 迁移，不在同一工程上交替使用不同 Editor。M0 读取并保存 `ProjectVersion.txt`、`Packages/manifest.json`、`Packages/packages-lock.json`，不凭经验填写包补丁版本。

### 1.2 MVP 成果

- **List Lab**：普通列表与虚拟列表的公平对照，展示对象池正确性、实例有界、位置恢复、动画 Wrapper 和单行更新实验。
- **Gradient Lab**：线性与非线性渐变、固定细分、安全降级及自适应细分实验，解释画质与 CPU/渲染成本的关系。
- **Benchmark Runner 与 playbook**：固定配置驱动、有效性检查、原始采样、报告生成、失败取证与复跑说明。
- **展示资料包**：可运行 Windows 展示构建，三个主题的图片、短视频、技术说明和可追溯实验数据，供未来个人主页使用。

### 1.3 范围边界

首期不复刻完整 LUI 库、登录/RPC/商城/车库、在线资源系统或个人主页。不把 UI 精修作为性能实验的前置条件。

Android 真机、WebGL、变高列表、高级 Shader 和其他组件进入后续扩展队列。缺少手机设备不阻塞 Windows MVP；没有真机证据时，不声明移动端性能结论。

参考材料保留原始语义；新工程使用独立实现及明确许可的第三方代码。所有结果区分“实习记录”“个人复现”“后续改进”，不将新项目的测量数据回填为实习原工程的历史实测。LoopScrollRect 的基础能力和个人改造分别说明。

## 2. 里程碑与依赖

按验收推进，不预设完成日期或性能提升百分比。默认顺序为 M0 → M1 → M2 → M3 → M4；每阶段完成一份可复查的交付，避免积累大量功能后才开始取证。

| 阶段 | 主题 | 前置条件 | 阶段成果 | 初始状态 |
|---|---|---|---|---|
| M0 | 最小测量闭环 | 版本决策已确认 | 简单 Case 在 Editor / Windows Player 运行，原始数据和报告可复跑 | 未开始 |
| M1 | 列表正确性与基准 | M0 通过 | List Lab 基线、契约测试、A/B 数据、第一段演示 | 未开始 |
| M2 | 渐变正确性与基准 | M0 通过；滚动集成场景依赖 M1 | Gradient Lab 基线、画质验证、静态/动态报告、第二段演示 | 未开始 |
| M3 | 两项深入优化 | 对应 M1 / M2 基线有效 | 单行刷新与自适应细分的独立实验和取舍结论 | 未开始 |
| M4 | 证据冻结与展示交付 | M1–M3 完成，测量协议已锁定 | Windows 构建、最终证据、三个主题素材和案例说明 | 未开始 |

M2 的独立渐变部分技术上只依赖 M0，默认仍先完成 M1，以复用第一次案例闭环的经验。M3 的列表和渐变实验分别依赖各自基线；本路线图不要求开启并行 Agent。

## 3. M0：最小测量闭环

目标：先证明工程可以运行、仪器可以读数、结果可以复跑。只使用最简单的 Image Case，不提前建设大型测试平台。

| 任务 ID | 工作 | 前置 | 交付物 |
|---|---|---|---|
| M0-01 | 检查目录与工具链，初始化 Git 和独立 Unity 工程；验证 Editor、匹配包与 Windows 构建模块 | 无 | 工程骨架、版本锁定、依赖与环境记录 |
| M0-02 | 建立最小场景，分离 Runtime、Editor 和测试程序集；验证 MCP 路由到本工程、编译、Play 和截图能力 | M0-01 | 可运行场景、构建入口、工具能力记录 |
| M0-03 | 实现 Case 接口、确定性 Runner、参数配置、计数器探测、采样和文件输出 | M0-02 | Image Case、原始样本、结构化摘要与 Markdown 报告 |
| M0-04 | 增加超时/取消/异常收尾、有效性判定和少量故障注入；在 Windows Development Player 复跑并校准测量协议 | M0-03 | 正常与失败样例、重复运行数据、初版 playbook |

M0-01 先核对已有内容，再确定工程根目录；默认使用 `UnityProject/`，将参考脚本留在 Assets 之外，避免误参与编译。初始化 Git 不等于公开仓库；公开交付范围单独管理。

Runner 至少覆盖 Prepare → Warmup → Measure → Validate → Export → Cleanup。正常结束、就绪超时、必要指标缺失、取消与异常均有明确状态和可追溯记录。关闭 Recorder、撤销事件订阅、清理运行对象等收尾逻辑应可重复执行。

**完成判据：**

- 指定版本可打开、编译和构建，最小场景运行窗口内无未解释异常。
- Editor 与 Windows Development Player 均产出有效样本，环境信息明确区分；命令或菜单入口可复跑。
- 启动时检查计数器有效性、类别、单位和样本数量；必要指标缺失判 invalid，不能输出零值冒充测量结果。
- 已知分配负载能够被识别，就绪超时和缺失指标能够产生失败/无效报告，不仅验证“成功路径”。
- 同配置重复运行的波动已记录，正式采样参数和比较规则形成初版；此阶段不宣称性能优化收益。

学习检查：解释帧间隔、CPU 工作时间、UI 标记耗时、分配字节和 GC 回收的区别，并指出采样代码自身可能造成的干扰。

## 4. M1：List Lab 正确性与基准

目标：重建 LUI 风格列表的核心契约，以可靠基线展示虚拟化和复用，优先处理分析报告指出的池归还缺口。

| 任务 ID | 工作 | 前置 | 交付物 |
|---|---|---|---|
| M1-01 | 核对并锁定 LoopScrollRect 上游提交、许可和适配边界；定义固定行高、模板、Bind/Unbind、滚动位置和池诊断契约 | M0 | 接口契约、第三方来源与改动记录 |
| M1-02 | 实现普通 ScrollRect 基线、虚拟列表、独立实例租赁登记与复用生命周期 | M1-01 | 两种列表实现、池正确性回归 |
| M1-03 | 接入位置恢复、动画 Wrapper、最小双模板正确性场景和边缘渐隐；加入可控诊断显示 | M1-02 | 展示场景、行为回归与截图 |
| M1-04 | 实现自动动作脚本，完成分阶段测量并制作第一份案例资料 | M1-03 | A/B 原始数据、图表、报告和短视频草稿 |

### 4.1 对照条件

两种列表使用相同数据、字体、素材、行高、视口、裁剪与动作脚本。普通列表按合理方式实现，不能人为每帧创建销毁来夸大差距；虚拟列表保留当前窗口刷新行为，供 M3 单行更新实验比较。

主性能矩阵先完成 N=100、1000，再扩展到 N=10000 压力档；可补 N=300 对应历史需求规模。若某基线在压力档超时或超出资源预算，保存失败证据和已完成的共同规模数据，不无限重试、不补造结果。

基准使用固定行高和单模板；双模板主要验证池路由正确性，不能将模板分布变化混入单模板性能结论。分别记录数据条数、可见数量、预取量、模板数和唯一实例数量。

### 4.2 场景与完成判据

| 场景 | 必须验证的行为 | 主要证据 |
|---|---|---|
| 冷开与再次打开 | 首次构建和预热复用分开计量 | 首次可交互耗时、创建数、峰值帧 |
| 静置与连续滚动 | 内容正确、实例有界、预热后固定负载不持续创建销毁 | 帧时序列、GC、池数量、生命周期计数 |
| 首尾跳转与切 Tab | index 与 offset 恢复符合约定，无残留惯性扰动 | 位置误差、内容索引、动作日志 |
| 重复归还与脏引用 | 同一实例不能被同时租给两个项；已销毁引用不能再使用 | EditMode / PlayMode 契约结果 |
| 清空重填与反复开关 | 绑定/解绑配对、动画复位、对象与资源数量收敛 | 轮次曲线、存活数量和异常日志 |
| Wrapper 与边缘渐隐 | 布局控制外层、动画控制内层；拖拽/滚轮触发正确，静止回零 | 状态断言、截图或演示视频 |

位置误差容差、预取/缓存预算与生命周期计数口径在 M1-01 定义，在比较前锁定。`active`、`leased`、`cached`、`templates` 分开报告：它们可能有重叠语义，不直接相加；唯一实例总数按实例身份去重，并另列未归属对象。

**M1 出口：**共同规模下的 A/B 有效数据齐全，正确性门槛通过；创建/绑定/UI 重建各自有证据；第一份列表说明图和演示已经产生。`cellMax=8` 不作为固定验收值。

学习检查：解释虚拟化减少哪些成本、哪些数据仍为 O(N)，并通过一次布局/动画冲突与一次归还错误说明原因和修复机制。

## 5. M2：Gradient Lab 正确性与基准

目标：实现独立渐变组件，验证原方案的可用范围，并为 M3 建立画质与性能基线。

| 任务 ID | 工作 | 前置 | 交付物 |
|---|---|---|---|
| M2-01 | 定义颜色乘法、方向、bias 数学语义、参数边界和降级契约 | M0 | 渐变契约与参考曲线 |
| M2-02 | 实现线性顶点色、固定 32 段非线性细分、严格矩形检查、顶点通道保留和变化才标脏 | M2-01 | 独立 GradientEffect 与正确性测试 |
| M2-03 | 建立大图、网格和裁剪列表场景，加入参数/网格可视化及图像验证 | M2-02；列表集成依赖 M1 | 功能截图、质量数据与展示场景 |
| M2-04 | 完成静态/动态矩阵、CPU 与渲染成本分析，制作第二份案例资料 | M2-03 | 原始数据、图表、报告和短视频草稿 |

### 5.1 功能与质量契约

- 验证端点、单调性、中心值、横纵方向、alpha 和极端 bias；“中心颜色比例”与“几何过渡位置”不得混为一个未经定义的概念。
- 四顶点线性路径和 32 段非线性路径分别验证几何、颜色与索引；保留兼容所需的顶点属性和 uv0–uv3。
- Simple、Sliced、Tiled、Filled/Radial 逐项说明支持或降级行为；非合法矩形不进入矩形细分，退化尺寸不产生 NaN、越界或塌陷网格。
- 参数相同重复赋值不应由该组件主动触发额外 dirty；静态无组件计算不等于无渲染成本。
- 使用固定输出尺寸、颜色空间和参考曲线/参考图，定义数值与图片容差。测试通道数据的保留与实际 Shader 输出，不仅观察默认白图。

### 5.2 最小实验矩阵

| 维度 | MVP 覆盖 |
|---|---|
| 功能状态 | Image only、组件关闭、静态开启、相同值重复赋值、持续改变参数 |
| 布局 | 单张大图、可见网格、裁剪列表 |
| 动态范围 | 少量元素变化与全部元素变化；针对代表用例比较同 Canvas 与动静拆分 |
| 规模 | 100、500、1000；流程有效后扩展到 2000、5000 压力档 |
| 指标 | 重建次数与 CPU 标记、帧间隔、GC、顶点/三角形、DrawCall/Batches、质量误差；GPU 耗时按支持情况记录 |

采用代表配置分层展开，不默认执行所有维度的笛卡尔积。每轮记录实际可见/裁剪状态；不能将“生成 5000 张图”写成“同时渲染 5000 张图”。

**M2 出口：**功能和降级契约通过；有静态、动态两类有效证据及质量对照；能够解释顶点增加、重建与合批的关系。无额外 DrawCall 和稳态 0 GC 只在测量确实支持的配置下声明，不作为预设普遍结论。

学习检查：解释为什么四顶点无法表达该非线性曲线、细分的成本在哪里，以及为什么更密网格不必然解决颜色量化色带。

## 6. M3：两项深入优化

目标：每条组件主线完成一次有基线、有假设、有质量约束的优化实验。结果可以是改进有效、仅部分场景有效或没有收益；保留负结果，禁止为获得漂亮数字改变比较条件。

| 任务 ID | 工作 | 前置 | 完成判据 |
|---|---|---|---|
| M3-L1 | 定位单行更新的额外绑定和实际 UI 重建成本，冻结窗口刷新基线 | M1 | 瓶颈证据、实验假设和指标明确 |
| M3-L2 | 实现可见 index→cell 映射与真正局部绑定，对照窗口刷新 | M3-L1 | 可见更新只绑定目标项；离屏更新不创建 cell；正确性通过，绑定与 CPU/Canvas 收益分别报告 |
| M3-G1 | 扫描 8/16/32/64 段，在多尺寸和 bias 下测量误差与成本 | M2 | 固定细分质量/成本曲线和预先定义的误差目标 |
| M3-G2 | 实现有上限和回退策略的自适应细分，与固定方案公平比较 | M3-G1 | 误差达标或明确标记超限；选择段数、重建、缓存成本全部计入，极端参数有证据 |
| M3-05 | 汇总两项实验，确定最终默认策略并复跑相关回归 | M3-L2、M3-G2 | 决策记录、前后对照、适用边界和学习复盘 |

局部绑定降低并不保证 Canvas 总耗时同幅下降；自适应段数减少也不保证 CPU 更快。若收益落在噪声范围内，结论应为 inconclusive；若持续更差，保留实验实现和结果说明，默认策略可以维持基线。

变高缓存、手工定位和 Shader 对照只在现有 profile 提出具体问题、且两项核心实验已形成结论后进入扩展，不替代 M3 必需交付。

学习检查：每项写一页“预测、证据、改动、收益/负结果、代价、适用边界”，用户能够独立解释其中一段 Profiler trace。

## 7. M4：证据冻结与展示交付

目标：把已完成实验整理为未来个人主页可直接使用的资料，完成可运行、可解释、可追溯的 Windows MVP。

| 任务 ID | 工作 | 前置 | 交付物 |
|---|---|---|---|
| M4-01 | 锁定最终代码/依赖/协议，复建并复跑代表矩阵，检查来源和结论一致性 | M3 | 最终证据索引、配置和运行清单 |
| M4-02 | 生成 Windows Release 展示构建，验证交互、功能与实际运行表现；与 Development 测量结果区分 | M4-01 | 展示包、运行说明、构建哈希与验证记录 |
| M4-03 | 从原始数据生成图表，独立录制展示与自动化失败示例 | M4-02 | 封面、说明图、短视频 |
| M4-04 | 编写三个主题的案例说明与复跑 playbook，整理交付目录并验收 | M4-03 | 完整展示资料包与 MVP 验收记录 |

### 7.1 三个主题的素材要求

| 主题 | 图片与视频 | 技术内容 |
|---|---|---|
| List Lab | 1 张封面、2–4 张说明图、30–60 秒 A/B 视频 | N 与实例数/冷开耗时关系、池契约、Wrapper、局部更新结果 |
| Gradient Lab | 1 张封面、2–4 张说明图、30–60 秒渐变与网格视频 | 曲线语义、降级边界、段数—误差—成本关系 |
| Agent 自动化测试 | 1 张封面、2–4 张流程/结果图、运行与报告短视频 | 配置驱动、有效性检查、失败被识别的示例、复跑方法 |

各主题配一份技术说明和实验结果索引。录屏不参与正式性能采样；视频中的实时叠层用于解释，最终数字引用独立测量 run ID。出现加速播放或跨运行拼接时注明。

### 7.2 MVP 总体验收

- 固定版本的工程、依赖和 Windows 展示包可运行；参考文件不参与工程编译。
- 两个组件案例及两项深入实验完成，核心正确性测试通过，所有未验证项和已知限制明确列出。
- 每项公开性能结论能定位到代码/构建、配置、硬件、原始数据、统计方法与来源运行。
- 自动化流程能够识别正常、失败和无效场景，失败不被输出为成功。
- 三个主题的图片、视频、说明和数据已齐备，无需先建设个人主页。
- 案例明确第三方来源、个人实现范围以及历史记录与新实验的区别；不承诺没有证据支持的性能改善。
- 用户完成两项核心实验的解释复盘；技术交付进度与学习复盘分别记录，复盘时间安排不阻塞常规实现与取证。

## 8. 统一实验与证据规则

这些规则适用于所有里程碑，具体配置在实验实施前落盘。修改协议后重新建立可比较数据，不拼接不同协议得出同一个改善百分比。

| 项目 | 规则 |
|---|---|
| 环境 | 记录 Unity/包版本、CPU/GPU、OS/驱动、图形 API、分辨率、Canvas/颜色空间、质量、VSync/帧率限制、脚本后端、Editor/Player、Development/Release |
| 输入 | 固定种子、数据、资源和动作时间线；记录可见数、模板数、预取与缓存配置 |
| 冷开 | 单独定义起止点并测量，不能预热后再称为冷开；与场景加载/进程启动区分 |
| 稳态起始协议 | 预热 300 帧、采样至少 1800 帧且覆盖完整动作、独立运行 5 次；M0 根据稳定性修订并版本化锁定 |
| 开发反馈 | 允许短 smoke run，但标记为开发检查，不进入正式性能结论 |
| 公平比较 | A/B 交错执行；按同配置比较每轮统计与轮间波动，不挑选最好一轮 |
| 帧时 | 保存原始序列；报告 p50/p95/p99、最大值与超预算帧比例；吞吐模式与 60 FPS 体验模式分开 |
| 分配与内存 | 分开记录分配、回收、存活对象及资源；无回收不等于零分配，内存曲线本身不证明无泄漏 |
| 指标能力 | 必要与可选指标在运行前确定；不可用记 unavailable，不能填 0；GPU 数据缺失不以 CPU 值替代 |
| 噪声 | 正式窗口不录屏、不截图、不逐帧打印或写文件；预分配缓冲，分析统计在采样结束后进行 |
| 诊断 | Deep Profiling、Frame Debugger、内存快照另跑并标记用途；无图形测试不能代替渲染与视觉验收 |
| 异常采样 | 保存焦点/暂停/超时事件；按预设规则判 invalid 并重跑，不临时删掉大帧使结果通过 |
| 结论 | 分开输出 correctness、measurement validity、performance comparison；保留 pass / fail / invalid / inconclusive |

M0 为基础 Case 确立必需指标；M1/M2 按待验证结论扩充，不把所有平台都无法保证提供的计数器列为全局硬门槛。相对性能阈值必须建立在已观察的基线波动上，不能先规定“必须优化 30%”。

每次运行至少保留 `config.json`、`environment.json`、`samples.csv`、`summary.json`、`report.md`、事件/错误日志。未进入采样的失败运行保留配置、环境、失败阶段和原因，不伪造样本。

正式证据记录 run ID、代码提交、依赖锁、构建与配置哈希、原始数据哈希；工作树有改动的运行标为探索性。正式基准尽量在干净的可复建提交上执行，生成产物置于输出目录，不因保存报告而混淆被测代码身份。

Agent 负责常规实现、构建、测试、诊断、图表和文档整理，按“先观察 → 提出假设 → 改一项 → 同条件复测 → 解释结果”推进。脚本与场景变更、运行验证、性能结论分别记录，不能以“代码写完”代替“已验收”。

任务交接保留当前工程路径、版本、最近有效运行、尚未解决的问题和下一步。清理只针对本次生成且归属明确的产物，不能为恢复“干净环境”覆盖用户已有改动。

## 10. 扩展队列与启动条件

| 扩展 | 启动条件 | 预期学习价值 |
|---|---|---|
| Android 真机基准 | Windows 代表矩阵有效，设备与构建链可用 | 移动 GPU、温度/功耗条件、CPU/GPU 瓶颈差异 |
| 变高列表与尺寸缓存 | profile 证明区间尺寸查询是实际热点 | 前缀和/Fenwick 树、缓存失效、时间与空间取舍 |
| 手工定位后端 | LayoutGroup 开销成为明确瓶颈 | 布局计算、接口隔离和行为兼容 |
| 渐变 Shader 对照 | CPU 重建或画质边界值得进一步研究 | 共享材质、参数传递、CPU/GPU 成本转移；同语义公平比较 |
| 异步头像与复用竞态 | 基础 Bind/Unbind 和池契约稳定 | 延迟/乱序、取消、版本保护、资源生命周期 |
| WebGL 交互展示 | Windows 素材包已完成，主页确需交互 | 浏览器约束、独立性能基线与分发体验 |
| CI 扩展 | 本地命令与失败状态稳定、收益明确 | 契约回归与产物归档；图形性能仍需适合的执行环境 |

这些扩展不影响 M0–M4 的完成定义。一次扩展只回答一个新增问题，避免在没有性能证据时扩大实现范围。
